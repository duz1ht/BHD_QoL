# DFBHD Raw Input / WM_INPUT Implementation Tech Summary

## Purpose

This document describes the planned implementation of modern Windows Raw Input mouse handling for `DFBHD.exe` while keeping the original executable unmodified on disk.

The compatibility layer will be implemented from a proxy DLL, such as `dinput8.dll`.

The goal is to replace the legacy gameplay mouse path based on `WM_MOUSEMOVE`, absolute cursor coordinates, and `SetCursorPos()` recentering with a Raw Input path based on `WM_INPUT` and relative mouse deltas.

The original DFBHD sensitivity, `mousescale`, `flipmouse`, action mapping, yaw, pitch, and gameplay logic should remain intact.

## Current DFBHD Mouse Path

The original game uses the Windows legacy mouse message path.

```text
Physical mouse
    ↓
Windows mouse stack
    ↓
WM_MOUSEMOVE / legacy button messages
    ↓
Thread message queue
    ↓
PollMouseInput()
    ↓
PeekMessageA()
    ↓
DFBHD mouse dispatcher
    ↓
Absolute cursor position
    ↓
Position relative to screen/window center
    ↓
Relative X/Y delta
    ↓
DFBHD internal mouse processing
    ↓
mousescale / flipmouse / bindings
    ↓
yaw / pitch / gameplay actions
```

The important limitation is that `WM_MOUSEMOVE` contains cursor position rather than native relative HID movement. The game therefore derives relative motion from cursor position and recenters the cursor with `SetCursorPos()`.

This is a legacy design and does not directly preserve the full event stream generated by modern high-polling-rate mice.

## Relevant DFBHD Locations

The current reverse-engineering identified the following relevant locations in this build:

```text

```

Important internal mouse state:

```text
0x00F655E0  Cursor X
0x00F655E4  Cursor Y
0x00F655E8  Mouse/button modifier state
0x00F655EC  Relative mouse X delta
0x00F655F0  Relative mouse Y delta
```

These addresses must be verified against the exact target executable build before runtime hooks are installed.

## Target Architecture

The modern path should be:

```text
Physical mouse
    ↓
Windows HID / Raw Input
    ↓
WM_INPUT
    ↓
Proxy dinput8.dll WndProc hook/subclass
    ↓
lParam = HRAWINPUT
    ↓
GetRawInputData() or GetRawInputBuffer()
    ↓
RAWMOUSE
    ↓
lLastX / lLastY / button flags / wheel
    ↓
DLL-side accumulators and state
    ↓
Hooked PollMouseInput()
    ↓
DFBHD relative X/Y and internal button events
    ↓
Original DFBHD processing
    ↓
mousescale / flipmouse / bindings
    ↓
yaw / pitch / gameplay actions
```

The DFBHD executable does not need to understand `WM_INPUT`, `HRAWINPUT`, `RAWINPUT`, or `RAWMOUSE`.

The DLL acts as a translation layer between the modern Windows input API and the legacy internal representation already consumed by DFBHD.

## Raw Input Registration

After the DFBHD game window has been created, the DLL should register the mouse with `RegisterRawInputDevices()`.

For the modern gameplay mode, the intended registration is equivalent to:

```cpp
RAWINPUTDEVICE rid = {};
rid.usUsagePage = 0x01;
rid.usUsage     = 0x02;
rid.dwFlags     = RIDEV_NOLEGACY;
rid.hwndTarget  = gameHwnd;

RegisterRawInputDevices(&rid, 1, sizeof(rid));
```

`RIDEV_NOLEGACY` is important because the same physical motion must not be processed simultaneously through both Raw Input and the legacy mouse-message path.

With `RIDEV_NOLEGACY`, legacy mouse messages for the registered mouse are suppressed for the application. This includes the normal `WM_MOUSEMOVE` path and legacy mouse-button messages.

The DLL therefore becomes responsible for translating both movement and mouse-button activity.

## WndProc Integration

The original DFBHD `WndProc` does not contain native `WM_INPUT` handling.

The proxy DLL should install a subclass or compatible hook around the game window procedure.

For `WM_INPUT`:

```cpp
case WM_INPUT:
{
    HRAWINPUT hRawInput = reinterpret_cast<HRAWINPUT>(lParam);

    // Read RAWINPUT data.
    // Extract relative movement, buttons, and wheel.
    // Store the translated result in DLL-side state.

    break;
}
```

The `lParam` of `WM_INPUT` must not be passed to DFBHD as mouse coordinates.

For `WM_INPUT`:

```text
lParam
    ↓
HRAWINPUT
    ↓
GetRawInputData()
    ↓
RAWINPUT
    ↓
RAWMOUSE
```

This is completely different from `WM_MOUSEMOVE`, where `lParam` contains packed cursor X/Y coordinates.

The modern `lParam` is consumed by the DLL only.

## Mouse Movement Translation

Raw Input exposes relative movement through:

```cpp
raw->data.mouse.lLastX;
raw->data.mouse.lLastY;
```

These values are signed `LONG` values.

The DLL should accumulate all relative reports received since the previous DFBHD mouse polling step:

```cpp
rawAccumX += rawX;
rawAccumY += rawY;
```

When the hooked `PollMouseInput()` is called, the DLL supplies the accumulated values to the same DFBHD internal delta fields that the original legacy path eventually produces:

```text
0x00F655EC = accumulated relative X
0x00F655F0 = accumulated relative Y
```

The DLL then clears its accumulators for the next polling interval.

Conceptually:

```cpp
DFBHD_MouseDeltaX = rawAccumX;
DFBHD_MouseDeltaY = rawAccumY;

rawAccumX = 0;
rawAccumY = 0;
```

The injection should happen before the original DFBHD stages that apply sensitivity and gameplay-specific processing.

The DLL should not inject directly into player yaw or pitch.

That would bypass original game behavior such as:

```text
mousescale
flipmouse
input/action bindings
context-sensitive processing
temporal/input distribution
pitch limits
player state rules
```

## Why PollMouseInput Is the Preferred Bridge

The cleanest design is to keep the original DFBHD input-processing pipeline and replace only the source of relative mouse data.

Original:

```text
PollMouseInput()
    ↓
PeekMessageA()
    ↓
WM_MOUSEMOVE
    ↓
absolute X/Y
    ↓
relative delta
```

Modern:

```text
PollMouseInput() hook
    ↓
DLL Raw Input accumulator
    ↓
relative X/Y already available
```

Everything after the relative-delta stage remains original DFBHD code.

This minimizes behavioral changes and makes the Raw Input mode easier to compare against the original implementation.

## Mouse Buttons

Because `RIDEV_NOLEGACY` suppresses the old mouse-button messages, the DLL must translate Raw Input button flags to the DFBHD internal mouse-event representation.

The currently identified DFBHD event codes are:

```text
0x02   Left button down
0x04   Left button up

0x08   Right button down
0x10   Right button up

0x20   Middle button down
0x40   Middle button up

0x100  Wheel positive
0x200  Wheel negative
```

The corresponding Raw Input flags include:

```text
RI_MOUSE_LEFT_BUTTON_DOWN
RI_MOUSE_LEFT_BUTTON_UP
RI_MOUSE_RIGHT_BUTTON_DOWN
RI_MOUSE_RIGHT_BUTTON_UP
RI_MOUSE_MIDDLE_BUTTON_DOWN
RI_MOUSE_MIDDLE_BUTTON_UP
RI_MOUSE_WHEEL
```

The DLL should translate each Raw Input transition to the equivalent DFBHD internal event instead of fabricating legacy Windows mouse messages.

Example:

```text
RI_MOUSE_LEFT_BUTTON_DOWN
    ↓
DLL updates persistent left-button state
    ↓
DLL emits DFBHD internal Left Down event
```

## Persistent Button and Modifier State

DFBHD also maintains a persistent state equivalent to the legacy mouse `wParam` state.

The currently identified state field is:

```text
0x00F655E8
```

Relevant legacy-style bits include:

```text
0x01  MK_LBUTTON
0x02  MK_RBUTTON
0x04  MK_SHIFT
0x08  MK_CONTROL
0x10  MK_MBUTTON
```

The DLL must maintain the mouse-button bits as Raw Input button transitions arrive.

Raw mouse input does not directly provide `MK_SHIFT` and `MK_CONTROL` in the same form that a legacy `WM_MOUSEMOVE` message did.

Therefore, when constructing the DFBHD-compatible state, the DLL should obtain Shift and Control state from the keyboard/input state and reproduce the corresponding bits.

This is necessary to preserve mouse bindings that depend on modifier keys.

## Mouse Wheel

For `RI_MOUSE_WHEEL`, `usButtonData` contains the signed wheel delta.

The original DFBHD behavior should be preserved, including the normal Windows wheel step of `WHEEL_DELTA` (120).

The DLL should accumulate wheel movement if necessary and emit the original DFBHD wheel events when the threshold is crossed:

```text
+120  → DFBHD event 0x100
-120  → DFBHD event 0x200
```

High-resolution wheel devices should not cause partial wheel data to be lost.

## High Polling Rate

For 1000 Hz, 2000 Hz, 4000 Hz, and 8000 Hz mice, all reports that arrive between two DFBHD input-consumption points should be retained.

Two implementation strategies are possible:

```text
WM_INPUT + GetRawInputData()
```

or:

```text
GetRawInputBuffer()
```

For very high report rates, buffered consumption is worth supporting because several Raw Input packets may be pending between game-loop iterations.

Regardless of the retrieval method, the DLL should accumulate the complete relative movement before handing the result to DFBHD.

Example:

```text
Report 1: +3, -1
Report 2: +4, -2
Report 3: +2,  0
Report 4: +5, -1

Accumulated:
X = +14
Y = -4
```

The game receives the accumulated relative motion for that consumption interval rather than depending on a coalesced cursor-position message.

## Cursor Recentering

The original gameplay mouse path depends on `SetCursorPos()` to place the Windows cursor back at the center after movement.

Raw Input relative motion does not require this.

Therefore, while Raw Input gameplay mode is active:

```text
SetCursorPos() must not be used as the source of mouse movement.
```

Cursor visibility and confinement can still be managed separately with APIs such as:

```text
ShowCursor()
ClipCursor()
```

Those APIs control the visible/system cursor but are not needed to calculate aiming movement.

## Menus

Raw relative movement and menu cursor positioning are separate problems.

The recommended initial implementation is:

```text
Gameplay:
    Raw Input
    RIDEV_NOLEGACY
    relative lLastX/lLastY
    no recenter-based aiming

Menus:
    preserve the original cursor-oriented behavior where practical
```

If switching registration modes between gameplay and menus proves unreliable, the DLL can maintain a virtual cursor for menus by integrating Raw Input deltas into an X/Y position and writing the values expected by the original menu code.

The first implementation should prefer compatibility over replacing menu behavior unnecessarily.

## Focus and Alt-Tab

The Raw Input layer must explicitly handle focus transitions.

On loss of focus:

```text
stop consuming gameplay movement
clear pending relative deltas
clear transient button transitions
release cursor confinement if active
allow the normal desktop cursor
```

On focus regain:

```text
clear stale Raw Input data
refresh window/monitor bounds
restore cursor confinement if needed
restore hidden cursor state if needed
resume Raw Input gameplay capture
ignore any invalid first movement generated by the transition
```

The Raw Input implementation should not depend on `SetCursorPos()` to recover from focus changes.

## DPI Awareness

DPI awareness is independent of Raw Input, but it is useful when cursor confinement, borderless mode, and window coordinates are involved.

The preferred compatibility declaration is an external or embedded application manifest containing basic DPI awareness.

Raw Input relative deltas themselves are not dependent on desktop pointer scaling in the same way as legacy cursor-position input.

## Configuration

The DLL should keep the original mouse path available as a fallback.

Suggested configuration:

```ini
raw_mouse_input = 0
```

Original DFBHD behavior:

```text
WM_MOUSEMOVE
legacy button messages
PeekMessageA
SetCursorPos recentering
```

Suggested modern mode:

```ini
raw_mouse_input = 1
```

Modern behavior:

```text
RegisterRawInputDevices
RIDEV_NOLEGACY
WM_INPUT
Raw relative movement
Raw button and wheel translation
DFBHD internal delta injection
```

A diagnostic option is also recommended:

```ini
raw_input_debug = 0
```

When enabled, it should log at least:

```text
Raw Input device
report count
accumulated X/Y
button transitions
wheel delta
DFBHD polling count
focus state
dropped/invalid packets if detected
```

## Implementation Rule

The compatibility layer should translate modern input into the format DFBHD already understands.

Do not attempt to make the original executable understand the Windows Raw Input structures directly.

The division should remain:

```text
Modern Windows side
    WM_INPUT
    HRAWINPUT
    RAWINPUT
    RAWMOUSE
    lLastX/lLastY
        ↓
    dinput8.dll translation layer
        ↓
Legacy DFBHD side
    relative X/Y
    internal button state
    internal mouse events
    original sensitivity
    original action system
    original yaw/pitch processing
```

## Validation Requirements

Before enabling the feature by default, compare Raw Input mode against the original implementation for:

```text
same effective sensitivity
same horizontal/vertical ratio
flipmouse behavior
button bindings
Shift + mouse bindings
Control + mouse bindings
wheel behavior
menu navigation
Alt-Tab and focus recovery
windowed/fullscreen behavior
125 Hz mouse
500 Hz mouse
1000 Hz mouse
2000 Hz mouse
4000 Hz mouse
8000 Hz mouse
multiple mouse devices
wireless mouse
high-DPI mouse settings
```

The Raw Input path should not change gameplay mechanics beyond removing the legacy cursor-based capture method.

## Summary

The planned implementation does not teach the 2004 DFBHD executable how to understand `WM_INPUT`.

Instead, the proxy `dinput8.dll` becomes the modern input backend.

It receives `WM_INPUT`, consumes the `HRAWINPUT` supplied through `lParam`, extracts relative mouse movement and button data, translates those values into the internal representation expected by DFBHD, and injects them at the existing mouse polling boundary.

The original DFBHD code remains responsible for sensitivity, inversion, bindings, action dispatch, yaw, pitch, and gameplay behavior.

This gives DFBHD a modern Raw Input mouse path while preserving as much of the original engine behavior as possible.
